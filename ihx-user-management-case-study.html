TL;DR

The whole story, in five cards.

Problem

No in-product way to manage users. Every action needed a person outside the hospital.

Risk

No quick way to deactivate a user, a real security concern for hospitals of any size, on a platform holding patient and financial data.

Solution

A discoverable, holistic UI for user management, designed around a real role hierarchy and real user needs.

Numbers

87% fewer support tickets. User creation 30 → 10 min. Deactivating a user: 4 steps → 1.

Takeaway

Problems users can solve themselves deserve product-led solutions, not process. Digging into this one surfaced real security lapses too.

01 — Problem Statement

User management operations lived outside the product, despite an in-product user management module.

The module existed. It was not solving the problem, and in one place, it was actively misleading users. Four problems defined the work.

80/day
Support tickets routed to Ops, every day
~50 user creations~30 password resets
1 The existing module went unused

Creation, editing, and disabling all existed as features. Hospital staff simply did not know the module was there.

2 No owner for access revocation

Deactivating a user meant email, to the account manager, to DB support: no one owned it end to end.

3 Group hospitals had a view, not control

Enterprise chains could see their centers, but could not manage a single user across them.

4 Feature enablement was an engineering burden

SSO, 2FA, and new users all routed through support, a project manager, and database engineering.

SSO, 2FA, and user role specific features needed an engineer to flip a DB flag User deactivation → a manual email chain: account manager, DB support, no time limit Tagged Revenue Innovation
The misleading detail

In the Account Details section, hospital staff could update their own bank details, believing insurers were automatically updated with that information. They were not.

02 — User Feedback & Pain Points

Support and account management pointed to the same root problem.

Not a summary. What the people closest to it actually said: hospital admins, the customer support team, and account management.

Account admin “I did not know user management was even a page in this product.”

The module existed. The people meant to use it never found it.

Visibility
Group hospital admin “I can see every center in my group. I cannot manage a single user in any of them.”

A centralized view with no centralized control: visibility without a single action to take.

Group Control
Account management “One deactivation meant an email, then a wait for DB support, then another wait.”

Most hospitals gave up partway. The account stayed active because revoking it took too long.

Access Revocation
Full feedback — Customer Support Team

“Every time we were enabling 2FA, the hospitals had a problem. Users forgot their emails, had not verified them, or used dummy emails to create a login. It became a painful, lengthy, manual process involving the account manager, the project manager, and the database support team. That broke the platform's stickiness: it pushed users out of the platform entirely, submitting claims by mail instead, because they were not able to log in.”

Platform Stickiness
03 — Product Gap

What the old module actually looked like.

Three screens carried most of the friction: the hospital's own profile, the modal used to create or edit a user, and group login itself.

Old screen — Hospital Profile

A user list squeezed into a side panel.

  • Account Details tab held one payer's bank information, dead weight once the platform went multi-payer
  • Infrastructure tab sat unused, standalone
  • User list was a side panel: no count, no visible access level, no clear call to action
Old screen — Create / Edit User

Permissions that did not match the product.

  • Profile picture upload nobody used
  • One Read Only / Edit toggle spanning six flat buckets, no read, write, export, or import split
  • Claims was a single bucket, not separated into PreAuth, Claim, and Reconciliation
Old screen — Group Login

Every module made you pick a center again.

  • Center had to be re-selected inside every module, no context carried over
  • A separate UI had to be built and maintained just for center-level login
  • The hierarchy of centers under a group was not retained anywhere
  • User management did not exist at the group level at all
Old vs. new
OldNew
Permission granularityRead Only / Edit, one toggleRead, Write, Export, Import per module
Module structureSix flat bucketsGrouped: Claims Module, Auto Reconciliation Module
HierarchyNoneGroup Admin → Group User / Center Admin → Center User

Scope expanded mid-project from single-center admins to Group Admins, tracking the group-hospital friction from Section 01.

The role hierarchy the product had to learn to represent
IHX Ops

Creates the first Group Admin, the only Ops-owned step left in v1

Group Admin

One admin, the whole chain, across every mapped center

Center Admin

Manages one center's team, scoped at login

Center User

Scoped to their own center's workflows

Group User

Cross-center visibility without admin rights

Group Admin, Group User, Center Admin, Center User: four roles where none existed.

A support ticket volume problem is rarely a support problem. Most of the time, it is a discoverability and trust problem with the solution that already exists.
